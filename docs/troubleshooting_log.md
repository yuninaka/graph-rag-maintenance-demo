### 2026-08-30 Symptom正規化(カテゴリ化)の実装と、そこで見つかった新たな課題

Q1・Q9のログで「未着手の根本対応」としていたSymptom正規化を実際に実装し、副次的に発覚した設計上の欠陥まで含めて記録する。

**実装内容**:
- `build_knowledge_graph.py` に `SYMPTOM_CATEGORIES`(異音/振動/圧力低下/発熱/温度上昇/停止/起動不良/動作異常/位置精度低下/冷却能力低下/バッテリー低下/部品損傷/汚損・劣化/その他 の14カテゴリ)を定義し、抽出プロンプトでLLMに1つ選ばせる方式(カテゴリ辞書方式)を採用
- `Symptom` ノードを自由記述の `name` ではなく `symptom_category` でMERGEするよう変更。元の自由記述は `HAS_SYMPTOM` 関係の `detail` プロパティに保持し情報を失わないようにした

**Cypher生成プロンプトの追加修正が必要だった**:
実装直後、Q1の生成Cypherが `Symptom {name: 'ベアリングの異音'}` と、質問文の言葉をそのまま`name`に当てはめてしまい、統制カテゴリの意味を理解していなかった(score変わらず0.00)。`GraphCypherQAChain`のデフォルトCypher生成プロンプトはこの前提を知らないため、`hybrid_agent.py`側で`cypher_prompt`をカスタマイズし、「`Symptom.name`はカテゴリ一覧からの統制語彙であり、質問文の言葉を意味的に近いカテゴリへマッピングしてから完全一致で検索する」という指示を明示的に追加した。これによりQ1は`count=3`を正しく返すようになった。

**しかし新たなバグを誘発した(グラフ設計の欠陥)**:
Symptomをカテゴリで共有ノード化した結果、`CAUSED_BY`を`Symptom → Cause`のまま張っていたため、Equipment条件で`ReportEvent`を絞り込んでも、その先の`Symptom → Cause`traversalが絞り込みをすり抜け、**同じカテゴリを持つ別設備・別報告書の原因まで混入**する事象が発生した(例: 「コンベアBの停止原因」にコンベアAやロボットの原因が混入。Q9では原因ごとの出現回数が実態と異なり全件「4」という不自然な値になった)。旧設計(Symptomが自由記述で実質1インシデント専用ノードだった)では表面化しなかった欠陥が、正規化によって顕在化した形。
- **対応**: `CAUSED_BY`を`Symptom → Cause`ではなく`ReportEvent → Cause`に変更(`docs/schema.md`参照)。Neo4jを再構築し、クロス混入が解消されたことをCypherで直接確認済み。

**修正後もscoreは0.80→0.70に一見悪化。ただし原因は2種類に分解できる**:
1. **golden_qaの期待キーワードが「report_id」を要求している構造的な問題(Q1, Q9)**: 修正後のCypher・回答は実態として以前より正確になった(Q9は不自然な「4回」×4件のクロス積が解消され、各原因が正しく「1回」ずつに)。しかしCypherがreport_idを返す設計になっていないため、golden_qaが要求する`R002`等のIDにヒットしない。皮肉なことに、以前スコアが高かったのは graph_query の回答が不十分だったためAgentが `vector_search` を併用し、そちらの文章からたまたまIDを拾えていたから。graph_query単体の回答が十分になった結果、Agentが vector_search を呼ばなくなり、ID自体が回答から消えた。
2. **Symptomの単一カテゴリ化という設計簡略化そのものの限界(Q5)**: R005(コンベアB)は本文が「異音および振動」としか書いておらず、LLMは(本文単体を見れば妥当な判断として)「異音」カテゴリに分類した。一方、後続のR017本文は「前回(R005)は取付ボルトの緩み」とR005を「停止」インシデントの一部として振り返っている。1レポート=1カテゴリという単純化では、こうした「表面的な症状」と「後から振り返った際の位置づけ」が食い違うケースを扱えない。
- **対応**: 今回はここで一区切りとし、上記2点を次回記事・今後の課題として記録するに留める(golden_qaの再修正、複数カテゴリ対応等の追加実装は行わない)。

**検討メモ: タグ付け方式(複数カテゴリ許可)は課題2を解決するか**:
1レポートに複数のSymptomカテゴリを許可する「タグ付け方式」を検討したが、Q5(R005)のケースは解決しないと判断した。R005自身の本文は「異音および振動」としか書かれておらず、タグ付け方式にすればこの2つは正しく拾えるようになる。しかし「R005が停止インシデントの一部だった」という情報は**R005自身の本文には存在せず、後続のR017の本文で初めて言及される**(「前回(R005)は取付ボルトの緩み」)。これは1レポートあたりの抽出をどれだけリッチにしても解決できない、**「1件ずつ独立抽出 vs 同一設備の過去レポート履歴を踏まえて抽出する」というアーキテクチャレベルの違い**の問題であり、タグ付け方式とは別軸の課題として記録するに留める(未実装)。

### 2026-08-30 Q5の残課題を解決:後方参照検出・差分更新方式

前項の「検討メモ」で記録した課題(「1件ずつ独立抽出 vs 過去レポート履歴を踏まえた抽出」というアーキテクチャレベルの問題)に、実際に着手した。

**当初案とスケール上の懸念**: 最初は「設備ごとに全履歴を1回のプロンプトにまとめて渡し、後続レポートの言及を踏まえて再判定する」2パス方式を検討したが、実装前にレビューした結果、履歴件数が数万件規模に増えるとコンテキストウィンドウ・精度・コストの面で破綻する設計だと判断し、不採用とした。

**採用した設計(スケールする差分更新方式)**: 抽出プロンプトに`backreferences`フィールドを追加し、「本文が過去の報告書ID(例: R005)を明示的に挙げて再解釈・補足している場合のみ」、そのIDと追加カテゴリを抽出するようにした。この情報が見つかった場合のみ、参照先の`ReportEvent`に軽量な追加`HAS_SYMPTOM`関係(`inferred_from`プロパティで由来を区別)を追記する。設備の全履歴を毎回読み直す必要がないため、レポート1件あたりの処理コストは履歴の総件数に依存せず一定に保たれる。

**結果**: R017の本文(「前回(R005)は取付ボルトの緩み、前々回(R008)はモーターのコイル絶縁不良が原因だったが...」)から、R005とR008への後方参照が正しく検出された。R005のSymptomノードは「異音」(自身の記述)と「停止」(R017による事後分類、`inferred_from: R017`)の2つに正しく紐づいた。Q5は score 0.75→1.00 に改善。全体スコアは 0.83→0.86。

- **対応**: 実装完了、コミット対象。
- **対応後の再評価結果**: graph 0.70→0.75、全体 0.83→0.86。Q1(0.25)・Q9(0.50)は今回のスコープ外(golden_qaのreport_id要求という別種の課題、記録済み)であり変化なし。

### 2026-08-30 後方参照検出の誤検出(false positive)を発見・修正

上記の実装検証中に、後方参照検出の**適合率(precision)の問題**を発見した。

**発見した誤り**: R035の本文「過去に4回類似トラブル(R002, R007, R015, **R022**関連)が発生している」から、R022への「圧力低下」backreferenceが抽出された。しかしR022自身の本文は「過去の圧力低下系トラブル(R002, R007, R015)**とは異なる症状**」と明示的に自分を区別しており(実際の症状は「振動」、原因は軸のアライメントずれ)、これは誤った後方参照だった。R035が複数の報告書IDを「類似」「関連」という緩い言葉でまとめて言及していたことが原因。

**影響**: Neo4j上でR022が「振動」と「圧力低下」の両方に紐づき、Q9(ポンプ3号機の吐出圧力低下原因)への回答が「合計5回」と、本来無関係なアライメントのずれまで含めるようになっていた。golden_qaのキーワード網羅率スコアはこの誤り(余計な内容の混入)を検知できず、scoreは0.50のまま変化していなかった(R005の正しい後方参照とは対照的に、こちらは静かに紛れ込んでいた)。

- **対応**: `EXTRACTION_PROMPT`のbackreferences抽出条件を厳密化。「報告書自身の症状を個別に言い切っている」場合のみ抽出し、「類似」「関連」といった緩い複数ID言及や、参照先が自ら「異なる症状」と明言している場合は抽出しないよう明示的な否定例を追加。「迷ったら含めない」という原則も明記。
- **対応後の再評価結果**: R035のbackreferencesは空配列になり、R022は「振動」カテゴリのみに正しく戻った。R005→R017の正しい検出(真陽性)は維持。全体スコアは0.86のまま変化なし(golden_qaが誤りを検知できていなかったため数値には表れないが、グラフの中身の正確性は改善)。

### 2026-09-01 Azure Document Intelligence連携: デジタルネイティブPDFでも視覚的な誤認識が発生

README 9.2の3番目「Azure Document Intelligenceの無料枠でOCR部分も実装」に着手。合成データ35件を`scripts/render_inspection_form.py`で点検記録表PDFにレンダリングし(正解データが既知)、`scripts/ocr_document_intelligence.py`でDocument Intelligence(`prebuilt-layout`モデル)に投げて抽出結果を正解と比較した。

**結果**: 35件中33件が完全一致(類似度1.0000)、平均類似度**0.9990**。ただし2件で興味深い誤りが見つかった。

- **R012**: 「継手の**O**リング(型番OR-14)」の「O」(アルファベット大文字)が「継手の**〇**リング」(丸記号)に誤認識された(類似度0.9944)
- **R013**: OCR結果の末尾に、正解データには存在しない`:unselected:`というタグが混入した(類似度0.9695)。帳票右下の「確認済」スタンプ(赤い円形の枠)を、チェックボックス的な選択要素として誤検出し「未選択」と判定したためと推測される

**発見の意味**: 今回のPDFはweasyprintで生成した、文字がテキストとして埋め込まれている「デジタルネイティブPDF」であり、素朴には「テキストレイヤーをそのまま抽出すれば文字認識の誤りは起きないはず」と想定していた。しかし実際にはアルファベット「O」と記号「〇」を混同するという、視覚的なOCR特有の誤認識が発生した。これは**Document Intelligenceが単純にPDFのテキストレイヤーを再利用しているのではなく、実際に画像として視覚的な認識処理を行っている可能性が高い**ことを示す。第3弾記事で書いた「目視でしか見つからない誤り」と同じ構図で、今回も9問のgolden_qa的な仕組みではなく、実際に全件を機械的に比較して初めて見つかった。

- **対応**: 実装(点検記録表PDF生成・Document Intelligence連携・比較スクリプト)は完了。文字レベルの誤認識(R012)・図形要素の誤検出(R013)はDocument Intelligence側の挙動であり、こちら側での対応(帳票レイアウトの調整、後段での文字補正等)は今回は行わず、発見事項として記録するに留める。
- **対応後の状態**: `scripts/render_inspection_form.py`(HTML+PDF生成)、`scripts/ocr_document_intelligence.py`(OCR精度検証、空白・改行・中黒表記ゆれの正規化込み)をコミット。

### 2026-09-01 パイプライン完成: OCR結果を既存パイプラインに接続、精度への影響を実測

前項で「未実装」としていた「OCR結果を`build_knowledge_graph.py`のパイプラインに接続する変換層」を実装した。これで「紙の書類(PDF)→OCR→ナレッジグラフ→ハイブリッド検索→回答」という一気通貫パイプラインが完成した。

### 2026-09-02 ベクトルインデックスをOCR由来データに接続、グラフ側との違いを実測

前項でスコープ外としていた`build_vector_index.py`をOCR由来データに対応させた。`build_knowledge_graph.py`と同じ`MAINTENANCE_LOGS_PATH`環境変数でデータソースを差し替え、Chromaの永続化先も`CHROMA_PERSIST_DIR`で分けられるようにした(合成データ版と混在させず、いつでも比較検証をやり直せるようにするため)。

**検証方法**: OCR由来データ(`data/maintenance_logs_ocr.jsonl`)でNeo4jとChromaを両方再構築し、`evaluate.py`を実行。結果を合成データ版(9問全問score=1.00)と比較した。

**結果**: graph 0.95(5件中1件が0.75に低下)、vector 1.00(4件)、全体0.97。

**原因**: Q5(コンベアBの停止原因、graph型)で発生。R005の原文は「モーター**取り付けボルト**の緩みが判明」(送り仮名あり)だが、OCR結果ではこの語の途中に空白が混入していた(「取り付けボ ルト」)。この崩れた文字列をLLMがエンティティ抽出する際、`cause`フィールドを「モーター**取付ボルト**の緩み」(送り仮名なし、R017本文で使われている別の表記ゆれと同じ形)に書き換えて出力した。golden_qaの期待キーワードは送り仮名ありの「取り付けボルト」のため、部分一致しなくなりスコアが低下した。

第4弾・前項で見つけたR012「O→〇」のケースは「壊れた文字列を正しい表記に補正する」という良い方向の自動修正だったが、今回は「壊れた文字列を、意味は同じだが表記の異なる別の正しい語に書き換える」というケースで、**LLMによる補正は必ずしも元の表記を再現するとは限らない**ことが分かった。golden_qaのキーワード部分一致という評価方法自体が、こうした表記ゆれに弱いという限界の表れでもある。

**ベクトル側は逆に、この空白混入をLLMで補正せず生のまま埋め込みに使っている**(`vs.get(where={'report_id':'R005'})`で実際に確認)。それでも多言語埋め込みモデル(intfloat/multilingual-e5-small)の意味的類似度計算はこの程度の空白混入に対しては頑健だったようで、vector型の4問はすべてscore=1.00を維持した。「OCRノイズがどう伝播するか」は、グラフ側(LLM抽出を経由し、書き換えられる可能性がある)とベクトル側(生テキストをそのまま埋め込む)とで異なる経路を辿ることが、今回の実測で確認できた。

- **対応**: `src/build_vector_index.py`・`src/hybrid_agent.py`に`MAINTENANCE_LOGS_PATH`/`CHROMA_PERSIST_DIR`環境変数対応を追加してコミット。Q5のスコア低下自体はOCR起因の表記ゆれであり、golden_qaのキーワードを追加修正する対応は今回は行わず、発見事項として記録するに留める(評価方法の限界の実例として第6弾記事にまとめる)。
- **対応後の状態**: 検証終了後、Neo4jは合成データで再構築し、`.env`の`LLM_PROVIDER`も`claude_code`に戻して元の状態に復元済み。合成データ版で再評価し9問全問score=1.00であることを確認済み。
